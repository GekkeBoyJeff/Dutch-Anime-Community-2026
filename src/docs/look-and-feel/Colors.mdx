## The two colorsets

A page is built from sections, and every section renders on either the light or the dark half of the
palette. `Section` takes a `colorset` prop and writes it onto the DOM as `data-colorset`; seven colours
and one focus ring swap underneath. `$primary` is listed with them so you can watch it do nothing —
the brand fill is the same colour on both halves. A section that says nothing keeps the half it is
nested in, and the page starts on light. Both halves, live:

<TwoUp>
	<Row fill="var(--background)" name="$background" note="The surface." />
	<Row fill="var(--color)" name="$color" note="Body text." />
	<Row fill="var(--color-secondary)" name="$color-secondary" note="Quieter text: intros, metadata." />
	<Row fill="var(--color-tertiary)" name="$color-tertiary" note="Quietest: placeholders, disabled labels." />
	<Row fill="var(--border)" name="$border" note="The hairline between two things." />
	<Row fill="var(--primary)" name="$primary" note="Does not flip: the same fill in both halves." />
	<Row fill="var(--primary-text)" name="$primary-text" note="The brand colour, kept readable as text." />
	<Row fill="var(--secondary)" name="$secondary" note="The quiet brand surface beside the accent." />
	<div style={{ marginBlockStart: '0.9rem' }}><span style={{ display: 'inline-block', padding: '0.4rem 0.8rem', borderRadius: '0.4rem', background: 'var(--background)', color: 'var(--color)', boxShadow: 'var(--shadow-focus)', fontSize: '0.8rem' }}>$shadow-focus</span></div>
</TwoUp>

There is one palette, and this is it. The only thing a section chooses is which half of it to stand
on.

## `--color` is the property, `$color` is the name you write

Two files, two forms of the same colour.

- `src/styles/theme.scss` declares the **custom property**: `--color: var(--color-light)`.
- `src/styles/_tokens.scss` declares the **Sass alias**: `$color: var(--color);`.

A component stylesheet always writes the `$` form:

```css
.section {
	background-color: $background;
	color: $color;
	padding-block: spacing(5xl);
	padding-inline: $section-gutter;
}
```

That is the whole of `src/styles/components/basics/Section.scss`. `_tokens.scss` is prepended to
every stylesheet by the build, so no component ever writes an `@use` line to reach these names.

> **Why two forms?** Sass runs at build time and cannot know which colorset a component will land in;
> the custom property is resolved by the browser, per subtree. The alias buys the short name without
> giving up the late binding — `$color` compiles to `var(--color)` and nothing more.

## What flips, and what does not

Exactly eight slots flip: `$background`, `$color`, `$color-secondary`, `$color-tertiary`, `$border`,
`$primary-text`, `$secondary` and `$shadow-focus`.

Everything else is a **fixed** colour that the component picks itself — the grey scale, the status
hues, `$primary`. A grey stays the same grey inside a dark section. When that is wrong, the component
says so, with the `on-colorset()` mixin:

```css
.badge {
	&.is-neutral {
		background-color: $grey-lightest;
		color: $color;

		@include on-colorset(dark) {
			background-color: $grey-dark;
		}
	}
}
```

Real code, from `src/styles/components/basics/Badge.scss`. The neutral badge is a near-white chip on
a light section; on a dark one that chip would glare, so it becomes a mid grey. Its text is `$color`,
which flips on its own and needs no extra rule.

The mixin compiles to a descendant selector — `[data-colorset="dark"] &` — so it matches any element
inside a dark section, however deep. Over 40 component stylesheets use it today.

## The grey scale

Seven fixed steps, in `src/styles/_tokens.scss`. They are plain Sass variables holding a hex value:
no `var()`, no flipping.

<Ramp steps={[['$white', '#ffffff'], ['$grey-lightest', '#f6f6f7'], ['$grey-light', '#e3e3e6'], ['$grey', '#a0a0a8'], ['$grey-dark', '#5c5c66'], ['$grey-darkest', '#202024'], ['$black', '#111112']]} />

The two halves are **not** built from these — the palette is plum and cream, which is why the panels
above are not grey. Reach for a grey when you need a neutral that stays the same in both colorsets: a
chip, an empty avatar, a skeleton.

## The brand colour

One saturated colour, and it does not flip — a primary button is the same yellow on a light
section and a dark one.

<TwoUp>
	<Row fill="var(--primary)" name="$primary" note="The fill: a primary button, an active tab." />
	<Row fill="var(--primary-hover)" name="$primary-hover" note="That fill while hovered or focused." />
	<Row fill="var(--primary-active)" name="$primary-active" note="That fill while pressed." />
	<Row fill="var(--tint-primary)" name="$tint-primary" note="A wash of it: a selected menu row." />
	<Row fill="var(--primary-text)" name="$primary-text" note="Flips. Use when the brand colour is text." />
	<Row fill="var(--secondary)" name="$secondary" note="Flips. The quiet surface beside the accent." />
</TwoUp>

`$primary-text` is the exception in this group, and the reason it exists: **dac** yellow is `#f5c24a`,
which is unreadable as text on white. The palette therefore keeps two values, and the colorset picks
one — `#875f0d` on the light half, `#f5c24a` on the dark half.

The label on a primary button is `$black`, and deliberately not `$color`: the fill does not flip, so
the text on it must not either. `$color` would turn cream on a dark section and leave 1.4 : 1 against
the gold. A fixed fill always takes a fixed text colour.

`$secondary` is a pair for the same reason the other way round. It is a surface rather than text, so
each half needs the value that stays *quiet* against its own background: **dac** uses cream `#f2ebd7`
on the light half and plum `#3b2938` on the dark half.

## Status colours

Four hues, the same in every colorset — success is green on a light section and on a dark one. Each
has a `tint` for backgrounds; three of them also have a `ring`, the hairline that outlines the box.

<TwoUp>
	<Row fill="var(--status-info)" name="$status-info" note="#1c7ed6" />
	<Row fill="var(--tint-info)" name="$tint-info" note="No $ring-info exists." />
	<Row fill="var(--status-success)" name="$status-success" note="#2f9e44" />
	<Row fill="var(--tint-success)" name="$tint-success" />
	<Row fill="var(--ring-success)" name="$ring-success" />
	<Row fill="var(--status-warning)" name="$status-warning" note="#e8590c" />
	<Row fill="var(--tint-warning)" name="$tint-warning" />
	<Row fill="var(--ring-warning)" name="$ring-warning" />
	<Row fill="var(--status-error)" name="$status-error" note="#e03131" />
	<Row fill="var(--tint-error)" name="$tint-error" />
	<Row fill="var(--ring-error)" name="$ring-error" />
</TwoUp>

The tints and rings are the hue at low alpha — `rgba($success, 0.14)` and `rgba($success, 0.32)` —
which is why they read differently over the two backgrounds while the solid hue does not. `Badge`
pairs the first two: `background-color: $tint-success` with `color: $status-success`. `Alert` adds the
third as an inset hairline: `box-shadow: inset 0 0 0 0.0625rem $ring-success`.

`$shadow-focus-error` is the matching focus ring for an invalid field, and it is a complete
`box-shadow` value rather than a colour: `0 0 0 0.1875rem rgba($error, 0.3)`.

## Two layers

`src/styles/theme.scss` is one file in two steps, and each step has exactly one job.

**1. Palette.** Every colour the site owns, as a `-light` and a `-dark` pair.

```css
:root {
	--primary: #f5c24a;
	--primary-text-light: #875f0d;
	--primary-text-dark: #f5c24a;

	--secondary-light: #f2ebd7;
	--secondary-dark: #3b2938;

	/* The light half. */
	--background-light: #ffffff;
	--color-light: #3b2938;
	--color-secondary-light: #6f5f6a;
	--color-tertiary-light: #948590;
	--border-light: #e7dcc0;

	/* The dark half — the same five slots, no more, no less. */
	--background-dark: #241a22;
	--color-dark: #f2ebd7;
	--color-secondary-dark: #c9b4bf;
	--color-tertiary-dark: #9a8792;
	--border-dark: #{rgba(#f2ebd7, 0.14)};
}
```

**2. Colorset.** Picks the light half or the dark half for one subtree. Written out twice on purpose:
every line reads `--x: var(--x-light)`, so what a colorset does is visible without decoding a loop.

```css
:root,
[data-colorset='light'] {
	--background: var(--background-light);
	--color: var(--color-light);
	--primary-text: var(--primary-text-light);
	--secondary: var(--secondary-light);
	--shadow-focus: 0 0 0 0.1875rem var(--primary-text-light);
}

[data-colorset='dark'] {
	--background: var(--background-dark);
	--color: var(--color-dark);
	--primary-text: var(--primary-text-dark);
	--secondary: var(--secondary-dark);
	--shadow-focus: 0 0 0 0.1875rem var(--primary-text-dark);
}
```

> **Why is `--shadow-focus` spelled out per colorset instead of built from `--primary-text`?** A custom
> property is resolved where it is *declared*, not where it is used. One written on `:root` would keep
> the root's accent even inside a nested dark section.

Restyling the whole site is step 1, and only step 1. Change the values in the `:root` palette; nothing
else in the codebase has to know.

`theme.scss` holds one more group: the `--admin-*` tokens. The staff platform has no palette of its
own — it reads everything above. What it owns is density: radii, gaps, row heights and three shadow
levels, because a tool wants a tighter rhythm than a marketing site.

## Which colour do I pick?

| I need… | Token | Flips? |
| --- | --- | --- |
| The surface of a section | `$background` | yes |
| Body text | `$color` | yes |
| An intro, a caption, metadata | `$color-secondary` | yes |
| A placeholder or a disabled label | `$color-tertiary` | yes |
| A divider, or a hairline around a card | `$border` | yes |
| A focus ring | `$shadow-focus` | yes |
| The brand colour **as text or an icon** | `$primary-text` | yes |
| The fill of a primary button | `$primary`, `$primary-hover`, `$primary-active` | no |
| The text or icon **on** that fill | `$black` | no |
| A quiet brand surface behind content | `$secondary` | yes |
| A selected row, an active filter chip | `$tint-primary` | no |
| A neutral chip or an empty avatar | a grey, plus `on-colorset(dark)` | no |
| Status text or a status icon | `$status-info` · `-success` · `-warning` · `-error` | no |
| The background behind that status text | `$tint-info` · `-success` · `-warning` · `-error` | no |
| The hairline outlining a status message | `$ring-success` · `-warning` · `-error` | no |
| The focus ring on an invalid field | `$shadow-focus-error` | no |
| The canvas around the rounded page frame | `$page` | no |
| A dialog backdrop | `$overlay`, `$overlay-strong` | no |

There is deliberately **no** token for "a slightly tinted box", and no `color-mix()` anywhere in the
token definitions. A box that needs to stand out uses a border, a shadow, or a grey with an
`on-colorset(dark)` rule.

## Adding a colour

1. `src/styles/theme.scss`, step 1 — add the value to the `:root` palette. If it has to flip, add the
   pair `--thing-light` and `--thing-dark`; if not, add plain `--thing`.
2. Same file, step 2 — if it flips, add one line to `[data-colorset='light']` and one to
   `[data-colorset='dark']`. Both blocks, always; a slot in one and not the other is a silent bug.
3. `src/styles/_tokens.scss` — add the alias next to its neighbours: `$thing: var(--thing);`.
4. Use `$thing` in the component stylesheet. Never `var(--thing)`.
6. Verify by compiling — `npm run storybook` or `npm run build`. An unknown Sass variable is a build
   error, so a missing step 4 cannot reach production. A missing step 3 can: nothing fails, the
   colour simply does not resolve inside that colorset. Hence both blocks, always.
