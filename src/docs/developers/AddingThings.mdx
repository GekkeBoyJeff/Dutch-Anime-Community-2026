# Adding things

The recipes. Each one lists every file and every wiring step in order, with the exact path, and says
what happens if a step is skipped.

The reasoning behind the rules — why props are a Zod schema, what a tier may import, how class names
are shaped — is on [2. Conventions](?path=/docs/for-developers-2-conventions--docs).

## Which folder?

| What is being added | Where it goes |
| --- | --- |
| A visual primitive with no state of its own — a chip, a title, a divider | `src/components/basics/` |
| A form control | `src/components/forms/` |
| A composed widget that holds state or handles interaction — a card, a dialog, a carousel | `src/components/components/` |
| A full-width section of a page — a hero, an FAQ, a band of figures | `src/components/contentBlocks/` |
| Part of the page shell — navigation, footer, announcement bar | `src/components/structures/` |
| Staff-platform shell UI | `src/components/dashboard/` |
| A reusable React hook | `src/hooks/` |
| A helper both halves of the app use | `src/lib/shared/` |
| A helper only the public site uses | `src/lib/site/` |
| A helper only the staff platform uses | `src/lib/admin/` |
| A page of the public site | `src/content/pages/<name>.ts`, then registered in `src/content/pages/index.ts` |
| Navigation, footer or announcement-bar data | `src/content/structures.ts` |
| An icon | the `ICONS` map in `src/components/basics/Icon/Icon.tsx` |
| An environment variable | `src/lib/shared/env.ts`, and documented in `.env.example` |
| A runtime API endpoint | `src/app/api/<name>/route.ts` — the four that exist are dynamic, so they only work on the `server` build target |

Two of those rows behave differently from the rest and are worth stating plainly:

- **`src/components/dashboard/`** takes plain TypeScript interfaces, not schemas. Its data comes from
  Supabase at runtime, not from the content layer.
- **`src/content/pages/`** is data, not code. Adding a page there needs no new component; see
  [4. Content & data](?path=/docs/for-developers-4-content-data--docs).

If a thing could plausibly go in two tiers, put it in the lower one. A basic can be used by
everything above it; a component cannot be used by a basic.

## Recipe: a basic, a component, a form field or a structure

The worked example is `Ribbon`, a basic that does not exist in this repo: a small angled label that
sits in the corner of a card and says something like "Nieuw". Substitute the tier folder from the
table above and the recipe is identical for all four tiers.

Four steps. The rightmost column is what goes wrong if the step is missed.

| # | Step | If skipped |
| --- | --- | --- |
| 1 | Write the schema: `src/lib/site/content/basics/ribbon.ts` | There is no props type to write the component against |
| 2 | Write the component: `src/components/basics/Ribbon.tsx`, its imports ending with its own stylesheet | Without that import line the stylesheet never reaches the bundle and the component renders unstyled |
| 3 | Write the stylesheet: `src/design-system/components/basics/Ribbon.scss` | The component renders unstyled |
| 4 | Write the story: `src/components/basics/Ribbon/Ribbon.stories.tsx` | The component is invisible in Storybook and cannot be reviewed |

Every step writes a file the component needs to work. There is no list to append to and no barrel to
keep in sync: a component imports its own stylesheet, so the only file that has to know `Ribbon.scss`
exists is `Ribbon.tsx`.

### 1. The schema

```typescript
// src/lib/site/content/basics/ribbon.ts
import { z } from 'zod';

export const RibbonProps = z
	.object({
		value: z.string().min(1).describe('The ribbon\'s visible text'),
		corner: z
			.enum(['start', 'end'])
			.optional()
			.describe('Which top corner the ribbon sits in; defaults to end'),
		className: z.string().optional().describe('Additional classes on the root element'),
	})
	.meta({ title: 'Ribbon' });
export type RibbonProps = z.infer<typeof RibbonProps>;
```

Every prop gets a `.describe()` — that text is what shows up in Storybook's args table. `.optional()`
marks the props the component supplies a default for.

### 2. The component

```tsx
// src/components/basics/Ribbon.tsx
import { classNames } from '@/lib/shared/classNames';
import type { RibbonProps as RibbonSchemaProps } from '@/lib/site/content/document/basics/ribbon';

import '@/design-system/components/basics/Ribbon.scss';

type RibbonProps = RibbonSchemaProps;

const Ribbon = ({
	corner = 'end',
	className,
	value,
}: RibbonProps) => {
	return (
		<span className={classNames('ribbon', `is-${corner}`, className)}>
			{value}
		</span>
	);
};

export default Ribbon;
```

Five things that are not optional:

- The last import is the component's own stylesheet, on its own line after a blank one. A global
  `.scss` only reaches the bundle when a module imports it, and the module that needs it is this one.
  ESLint leaves the line alone: `import/order` does not sort imports that bind no name.
- The type import points at **the schema file**, never at `@/lib/site/content` — that barrel is
  server-only and will fail the build if it reaches the browser.
- The component is an arrow function assigned to a `const`, and it is the **default** export. ESLint
  rejects a `function` declaration.
- `classNames` takes the root class first, the modifiers next, and the caller's `className` last.
- Imports: external packages, blank line, then `@/` paths in alphabetical order. `npm run lint`
  checks this.

A form field additionally needs `'use client'` on the first line, because the form tier wraps Base
UI, whose components use state and effects. Every file in `src/components/forms/` carries it except
`FieldGroup.tsx`, which is a plain wrapper element.

### 3. The stylesheet

```css
/* src/design-system/components/basics/Ribbon.scss */
.ribbon {
	--font-size: 0.75rem;
	position: absolute;
	inset-block-start: spacing(l);
	padding-block: spacing(xs);
	padding-inline: spacing(s);
	background-color: $primary;
	color: $white;
	font-weight: $weight-semibold;

	&.is-start {
		inset-inline-start: 0;
	}

	&.is-end {
		inset-inline-end: 0;
	}
}
```

No `@use` and no import line: `spacing()`, `$primary` and `$white` are prepended to every stylesheet
by the build. One top-level selector, every child class prefixed with the root class, modifiers as
bare `&.is-…`, everything nested. Never BEM.

### 4. The story

```tsx
// src/components/basics/Ribbon/Ribbon.stories.tsx
import type { Meta, StoryObj } from '@storybook/nextjs-vite';

import Ribbon from '@/components/basics/Ribbon';
import { RibbonProps } from '@/lib/site/content/document/basics/ribbon';

const meta: Meta<typeof Ribbon> = {
	title: 'Basics/Ribbon',
	component: Ribbon,
	parameters: {
		docs: { description: { component: 'A small angled label pinned to the corner of a card.' } },
		jsonSchema: { schema: RibbonProps },
	},
	argTypes: {
		corner: {
			control: 'inline-radio',
			options: ['start', 'end'],
		},
	},
};

export default meta;

type Story = StoryObj<typeof Ribbon>;

export const Default: Story = {
	args: {
		value: 'Nieuw',
	},
};

export const StartCorner: Story = {
	args: {
		...Default.args,
		corner: 'start',
	},
};
```

`title` is `Tier/Component`. The **schema value** is imported alongside the component and passed as
`jsonSchema: { schema: RibbonProps }`; that gives the story a JSON Schema panel and validates the
args on every render, so a bad arg is reported instead of silently rendering wrong.

### Then

```bash
npm run verify
npm run storybook
```

`verify` is typecheck, lint and every stylesheet compiled and imported. That plus looking at the
story is the whole verification loop.

## Recipe: a content block

A content block is a component in `src/components/contentBlocks/` — so the four steps above all
apply, unchanged, with `basics` swapped for `contentBlocks` in every path. What follows is
everything that is *extra*.

The worked example is `PosterWall`, a block that does not exist in this repo: a grid of poster images
with a heading above it.

| # | Extra step | If skipped |
| --- | --- | --- |
| A | The schema also exports a `…Block` variant with a `type` literal | The build stops and names the folder: a content block needs that literal |
| B | That variant's `.meta()` names a `category` | The block lands in the editor's "Overig" group |
| C | Give the story a `Default` export with `args` | The editor inserts placeholder values like "Tekst" |

All three live in the block's own folder. The `Block` union and the render registry are **generated**
from the folders under `src/components/contentBlocks`, so a new block registers itself by existing.

### A. The schema has two exports

A block schema exports the props *and* a block variant. The block variant is the props plus a `type`
discriminator and an optional `id`. `StatBand` is the pattern to copy:

```typescript
// src/components/contentBlocks/StatBand/StatBand.schema.ts
export const StatBandProps = z
	.object({
		colorset: Colorset.optional().describe('Light/dark theme applied to the surrounding section'),
		heading: Heading.optional().describe('Heading cluster (tagline, title, intro) shown above the figures'),
		items: z.array(StatBandItem).min(2).max(4).describe('The key figures rendered in the band'),
	})
	.meta({ title: 'StatBand' });
export type StatBandProps = z.infer<typeof StatBandProps>;

export const StatBandBlock = StatBandProps.extend({ type: z.literal('statBand'), id: Id.optional() });
export type StatBandBlock = z.infer<typeof StatBandBlock>;
```

The `type` literal is camelCase and is the block's identity everywhere else: in the union, in the
render registry, and in the JSON stored for a page. `Colorset`, `Heading` and `Id` come from
`src/lib/site/content/shared.ts`, which holds the shapes several blocks share — reuse
them rather than re-declaring a heading.

So `posterWall.ts` would end with:

```typescript
export const PosterWallBlock = PosterWallProps.extend({ type: z.literal('posterWall'), id: Id.optional() });
export type PosterWallBlock = z.infer<typeof PosterWallBlock>;
```

### B. The editor category

The block variant's `.meta()` says which group it belongs to in the editor's insert panel:

```typescript
export const PosterWallBlock = PosterWallProps.extend({
	type: z.literal('posterWall'),
	id: Id.optional(),
}).meta({ category: 'grids' });
```

The five group names and their Dutch labels live in `src/lib/admin/puck/config.tsx`, which reads this
`category` and groups the blocks itself. `other` is where a block with no category lands, so leaving
it out is not a bug, just an untidy panel.

### The generated registry

Two things still have to know about every block: the `Block` union that validates page content, and
the map from a `type` to the component that draws it. Neither is written by hand.

```
src/components/contentBlocks/Blocks/
	Blocks.tsx                      the renderer
	Blocks.schema.generated.ts      the Block union
	Blocks.registry.generated.ts    type → component
```

`scripts/generate-blocks.mjs` scans the folders under `src/components/contentBlocks` and writes both.
It runs when `next.config.mjs` or `.storybook/main.js` is imported — the same trick
`styles.config.mjs` uses for `_breakpoints.scss` — so `npm run dev` and every build regenerate them.
Add a block while the dev server is running and you have to restart it once.

They are two files rather than one on purpose. The union has to be reachable without pulling in React
components, or every route that knows what a `Page` is would ship every block's CSS.

The generator fails loudly on a folder it cannot read: a missing `<Name>.schema.ts`, a missing
`<Name>Block` export, or a missing `type: z.literal('…')` each stop the build with that folder's name.

Because both files come from the same scan, a block can no longer be in one list and not the other.
What still gets checked is the part a generator cannot know — whether a component's props match its
schema — and that check is one line in `Blocks.tsx`:

```tsx
export const REGISTRY: BlockRenderers = RENDERERS;
```

`BlockRenderers` is a mapped type over the `Block` union, so a component whose props drifted from its
own schema fails `npm run typecheck`.

### C. The story doubles as the editor's presets

Which is the one step with real constraints attached, so it has its own section below.


## Story args are the editor's presets

`src/lib/admin/puck/presets.ts` imports the content-block stories through the bundler and turns each
one into a preset an editor can insert. Nothing is declared twice: a story that looks right in
Storybook is a starting point in the editor for free.

The loop that does it:

```typescript
// src/lib/admin/puck/presets.ts
const stories = require.context('../../../stories/contentBlocks', false, /\.stories\.tsx$/);

for (const key of stories.keys()) {
	const mod = stories(key) as StoryModule;
	const type = typeByComponent.get(mod.default?.component);
	if (!type) {
		continue;
	}
	// …
	for (const [exportName, story] of Object.entries(mod)) {
		if (exportName === 'default' || !story || typeof story !== 'object') {
			continue;
		}
		const { args } = story as { args?: object };
		if (args && typeof args === 'object') {
			blockPresets.push({ label: humanise(exportName), props: sanitise(args) });
		}
	}
}
```

Which puts five constraints on a content-block story:

| Constraint | Why |
| --- | --- |
| The file sits in the block's own folder under `src/components/contentBlocks/`, named `<Name>.stories.tsx` | `require.context` scans that tree for exactly that pattern |
| `component:` in the story's default export is the same component the registry holds | Presets are matched by component identity, through `typeByComponent.get(mod.default?.component)`. A wrapper or a re-declared copy matches nothing and the block silently gets no presets |
| Every named export with an `args` object becomes a preset | There is no opt-out. A story that only exists to demonstrate a broken state will be offered to editors |
| Args must be plain JSON — no functions, no JSX, no `undefined` values | `sanitise` does `JSON.parse(JSON.stringify(args))`, which drops all three |
| One export should be called `Default` | `defaultPresetFor` looks for the preset labelled `Default` and falls back to the first one. That preset is what an editor gets when they drag the block in |

Two conveniences the harvester adds on top:

- **Item ids are backfilled.** Any object inside an array that has no `id` gets a fresh
  `crypto.randomUUID()`, so item schemas that require an `id` stay valid. Writing `id: 's1'` in a
  story is still clearer to read.
- **Export names are humanised.** `humanise` splits on the camelCase boundary and sentence-cases the
  result, so `WithHeading` is shown to the editor as "With heading". Name the exports accordingly.

If a block has no story with args at all, the editor falls back to `defaultValueFor` in
`src/lib/admin/puck/fields.tsx`, which invents a value per prop: `'Tekst'` for a string, `0` or the
minimum for a number, the first option of an enum, `false` for a boolean. That is the source of the
placeholder text that occasionally appears in the editor.

### Which Zod type becomes which input

The editor derives its form from the schema, so the Zod type chosen in step A decides what an editor
sees. `fieldFor` in `src/lib/admin/puck/fields.tsx` maps:

| Zod type | Editor input |
| --- | --- |
| `z.string()` | a text box |
| `z.string().meta({ editor: 'textarea' })` | a multi-line box |
| `z.string().meta({ editor: 'richtext' })` | a rich-text editor |
| `z.string().meta({ editor: 'icon' })` | a dropdown of the `ICONS` names |
| `z.string().meta({ editor: 'file' })` | a picker over the Supabase `media` bucket |
| `z.number()` | a number input, with `min`/`max` carried over |
| `z.enum([…])` | a dropdown |
| A union of literals only | a dropdown |
| `z.boolean()` | a Ja/Nee radio pair |
| `z.array(z.object({ … }))` | a repeatable list |
| `z.array(z.string())` | a line-per-item textarea |
| `z.object({ … })` | a nested group of inputs |
| **Anything else** | **nothing — the prop is not editable, with no warning** |

A key named `id` is skipped on purpose: ids are generated, not typed.

## Recipe: a third-party dependency

Three things have to line up: the install, the client boundary, and the Content Security Policy.

### 1. Install it

```bash
npm install <package>
```

Runtime dependencies belong in `dependencies`. Anything used only by Storybook, the build scripts or
the type layer belongs in `devDependencies`.

### 2. Wrap it in a `'use client'` island

A library that touches the DOM, holds state or reads `window` cannot run in a server component. The
wrapper around it gets `'use client'`, and it should be the *only* file that does, because the
directive is inherited by everything that file imports.

`Swiper` is the pattern to copy — it wraps `embla-carousel-react`:

```tsx
// src/components/components/Swiper/Swiper.tsx
'use client';

import useEmblaCarousel from 'embla-carousel-react';
import { useCallback, useEffect, useState } from 'react';

import Content from '@/components/basics/Content/Content';
import Interactive from '@/components/basics/Interactive/Interactive';
import Media from '@/components/basics/Media/Media';
```

The blocks that use `Swiper` stay server components. They render it as a child, pass it serialisable
props, and ship no JavaScript of their own. Keeping the island small is the entire point: everything
outside it is HTML by the time it reaches the browser.

Note the shape of that wrapper. The library's API does not leak upward — callers see this project's
prop names, taken from the schema, not Embla's. That is what makes the library replaceable later.

### 3. Check the Content Security Policy

`next.config.mjs` sets a Content Security Policy — a header that tells the browser which origins a
page may load things from. Anything the policy does not list is blocked. The policy is one template
literal:

```typescript
// next.config.mjs
const cspHeader = `
	default-src 'self';
	script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval';
	worker-src 'self' blob:;
	style-src 'self' 'unsafe-inline';
	img-src 'self' blob: data: ${supabaseOrigin};
	font-src 'self';
	connect-src 'self' ${supabaseOrigin} ${supabaseWs};
	frame-src 'self' https://www.youtube-nocookie.com https://player.vimeo.com https://www.tiktok.com https://fast.wistia.net https://fast.wistia.com;
	object-src 'none';
	base-uri 'self';
	form-action 'self';
	frame-ancestors 'none';
`
```

What each directive gates, and what to do about it:

| If the dependency… | The directive | What to add |
| --- | --- | --- |
| Loads a script from a CDN | `script-src` | the origin — or better, install the package so it is bundled and served from `'self'` |
| Loads a stylesheet from another origin | `style-src` | the origin |
| Loads a webfont from another origin | `font-src` | the origin |
| Loads images from another origin | `img-src` | the origin |
| Calls an HTTP API or opens a WebSocket | `connect-src` | the origin (a socket needs the `wss:` form too) |
| Embeds an iframe | `frame-src` | the origin |
| Starts a web worker | `worker-src` | usually nothing — `'self' blob:` is already allowed |

Two things about this policy catch people out:

- **It is not applied in development.** `headers()` returns an empty array when `NODE_ENV` is
  `development`, so a blocked resource works locally and fails only after `npm run build` and
  `npm start`. Test the production build before believing an embed works.
- **It is not applied on the static target either.** When `HOST_TYPE=static` the config takes the
  `output: 'export'` branch, which has no `headers()` at all — a static host would have to send the
  headers itself.

`/builder` gets its own slightly relaxed copy (`builderCspHeader`) for the editor's webfont. It is
derived from the same string by three `.replace()` calls, so a change to the main policy carries
over — unless the change happens to alter one of the three substrings those calls match on.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| The component renders, completely unstyled | The component file has no `import '@/design-system/components/…'` line, so its stylesheet never reached the bundle |
| `npm run typecheck` says a property is missing from `REGISTRY` | The block is in the union but has no renderer in `Blocks.tsx` |
| `npm run typecheck` flags an unknown key in the `REGISTRY` object | An entry whose `type` no block schema declares |
| The build stops with `✖ Invalid page content — 2 problems:` and a field path | A page in `src/content/pages/` no longer matches the schema. The message names the page and the field |
| A prop is in the schema but has no input in `/builder` | `fieldFor` could not map that Zod type and returned `undefined`. See the mapping table above |
| A new block appears in `/builder` under "Overig" | It is not listed in any `categories` entry in `src/lib/admin/puck/config.tsx` |
| Dragging a block in gives placeholder text like "Tekst" | The block has no story with `args`, so `defaultValueFor` invented a value per prop |
| A story exists but the block has no presets | The story file is not under `src/components/contentBlocks/`, or `component:` is not the same component object as the one in `REGISTRY` |
| A preset is missing a prop that the story clearly sets | The value was a function, JSX or `undefined`; `sanitise` JSON round-trips the args and drops all three |
| `<Icon name="…" />` renders nothing at all | The name is not a key in the `ICONS` map in `src/components/basics/Icon/Icon.tsx`. `Icon` returns `null` for an unknown name |
| A build error mentioning `server-only` | Something reaching the browser imports `@/lib/site/content`. Import the specific schema file instead |
| `npm run lint` complains about `import/order` | Imports out of group order, missing a blank line between groups, or not alphabetical within a group |
| `npm run lint` complains about `func-style` or `react/function-component-definition` | A `function` declaration. Everything is an arrow function assigned to a `const` |
| A prop was added to the schema and nothing changed on screen | The component still has to destructure it and render it. The schema describes props; it does not render them |
| An embed, font or external script works in `npm run dev` and breaks in production | The CSP is skipped in development. Add the origin to the right directive in `next.config.mjs` |
| `next dev` hangs after a production build | Turbopack is choking on a stale webpack cache. `rm -rf .next` |

## Before calling it done

- `npm run typecheck` passes.
- `npm run lint` passes.
- The story opens in `npm run storybook`, and the **JSON Schema** panel lists no issues.
- The component looks right on a light *and* a dark section. Storybook's dark-mode toggle flips
  `data-colorset` on the preview body; blocks with a `colorset` prop also have their own control.
- For a content block: `npm run dev`, open `/builder` ([9. The visual editor](?path=/docs/for-developers-9-the-visual-editor--docs)), insert the block, and confirm that every prop
  has an input and that the default preset fills it in sensibly.
