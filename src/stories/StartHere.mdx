# Start here

One codebase holds two things: the public Dutch Anime Community website, and the staff platform the
volunteers run it from. This page covers what those two are, how this Storybook is organised, how to
start both servers, and which file to open for a given change.

## The two halves

**The public site.** A Dutch-language marketing site for an anime community that lives on Discord.
Every page exists to move a visitor towards joining. It is small: `src/content/pages/index.ts`
registers five paths, and `src/content/pages/notFound.ts` holds the 404.

```typescript
// src/content/pages/index.ts
export const pages: Record<string, Page> = {
	'/': homePage,
	'/community': communityPage,
	'/evenementen': evenementenPage,
	'/supporters': supportersPage,
	'/word-lid': wordLidPage,
};
```

Those pages are rendered ahead of time, into HTML, and served as files. Nothing runs per visitor.

**The staff platform.** The same app behind a Discord login, talking to a Supabase (Postgres)
database straight from the browser. Six routes exist today: `/login` and `/auth/callback` handle the
Discord sign-in, `/builder` is the visual page editor ([9. The visual editor](?path=/docs/for-developers-9-the-visual-editor--docs)), `/enquete` fills in a survey, and `/account`
and `/upload` are still placeholders that render a heading and nothing else. The database underneath
is much further along than the screens — `supabase/migrations/` holds 83 SQL files.

Site content is written in **Dutch**. Code, comments and these docs are in **English**.

> **Why one repository?** The staff platform is built from the same components as the site.
> `src/components/dashboard/shell/DashboardNav.tsx` imports `Icon`, `Media`, `Shortcut` and
> `Skeleton` from `@/components/basics/`, and the login screen uses the same `Button`. A change to a
> primitive lands in both halves at once.

This codebase started life as a reusable Next.js starter written by Jeffrey Ullers, and the Dutch
Anime Community site is what that starter grew into. That explains two things that would otherwise
look odd: no component is named after DAC, and two extra colour themes ship alongside the brand one.

## What this Storybook is

Storybook renders each component on its own, outside any page, so it can be inspected and poked at
without clicking through the site. The sidebar has two kinds of entry: prose pages, and component
catalogues.

| Section | What is in it | Who it is for |
| --- | --- | --- |
| **Start here** | This page. | Everyone. |
| **For developers** | Eight numbered pages, written to be read in order. | Anyone writing code here. |
| **Look & feel** | [Colors](?path=/docs/look-feel-colors--docs), [Typography](?path=/docs/look-feel-typography--docs) and [Spacing](?path=/docs/look-feel-spacing--docs) — the design system, rendered from the real stylesheets. | Designers, and any developer picking a value. |
| **Basics · Components · ContentBlocks · Structures · Forms · Dashboard** | The component catalogue. Every component gets a **Docs** tab (props table plus examples) and a **Canvas** tab (the component alone). | Both. |

The sidebar order is not alphabetical — it is set explicitly in `.storybook/preview.tsx` under
`options.storySort`.

### The toolbar controls

Three toolbar controls change what the canvas shows. All three are configured in
`.storybook/preview.tsx`.

| Control | What it changes |
| --- | --- |
| Sun/moon | Sets `data-colorset` to `light` or `dark` on the preview body — the same switch a dark section uses on the real site. |
| **Theme** | Sets `data-theme` on the root element: `dac` (what the site ships, and the default here), `sepia`, or `default`. |
| **Direction** | Sets `dir` to `ltr` or `rtl`. |

The two non-brand themes are not decoration. They are the check that no component has hard-coded a
colour: if something looks wrong in `sepia`, a value was written that should have been a token.

## Running it

Node 22 or newer. That version is stated in three places — `.nvmrc` contains `22`, `package.json`
declares `"engines": { "node": ">=22" }`, and both GitHub Actions workflows pin `node-version: 22`.
The reason is in `README.md`: the Supabase client needs a global `WebSocket`, which older Node does
not have. Note that `engines` is a declaration, not a lock — npm warns, it does not stop you.

```bash
node -v                      # v22 or higher
npm install
cp .env.example .env.local    # then fill in the Supabase values
npm run dev                   # the site   → http://localhost:3000
npm run storybook             # these docs → http://localhost:6006
```

`.env.example` is a commented template; it lists which values are required and which are optional.
Every variable is validated at startup by `src/lib/shared/env.ts`, and the optional ones default to
"off" — so the app boots without a Supabase project, it just cannot log in or open `/builder`.

### The scripts

Straight from `package.json`:

| Command | What it does |
| --- | --- |
| `npm run dev` | `next dev`. Port 3000. `/builder` is on in development. |
| `npm run dev:local` | The same with `CONTENT_SOURCE=registry`, which forces page content to come from the files in `src/content/`. |
| `npm run storybook` | This documentation, on port 6006. |
| `npm run typecheck` | `tsc --noEmit`. `strict` plus `noUncheckedIndexedAccess`. |
| `npm run lint` | `eslint .` |
| `npm run build` | The production build: optimise images, then build with the service worker enabled. |
| `npm run build:plain` | Optimise images, then a plain build without the service worker. |
| `npm run images` | Regenerates the responsive image variants and the media list `/builder` picks from. |
| `npm run seed` | One-off: writes the files in `src/content/` into the database. Read the warning below before running it. |
| `npm run db:push` | Applies the SQL migrations to the linked Supabase project, then regenerates the types. |
| `npm run db:types` | Regenerates `src/types/database.types.ts` from the linked project. Run it after every schema change. |

> **There is no test runner.** No `vitest`, no `jest`, no `test` script. "Verified" here means
> `npm run typecheck` and `npm run lint` both pass, plus a build — the build validates every page's
> content against the schema and fails with the offending field named. See
> [5. Validation](?path=/docs/for-developers-5-validation--docs).

## Where does my change go?

| To change… | Open | Notes |
| --- | --- | --- |
| The words on a page | `src/content/pages/<page>.ts` | Read the warning below first. This is often not what the live site serves. |
| The header, footer or announcement bar | `src/content/structures.ts` | Same warning. |
| How a component looks | `src/styles/components/<tier>/<Name>.scss` | One stylesheet per component, in a folder tree mirroring `src/components/`. Restyling the button is `src/styles/components/basics/Button.scss`. |
| A brand colour | the `[data-theme='dac']` block in `src/styles/theme.scss` | A few runtime surfaces cannot read CSS — the browser theme colour and the share image — and repeat the palette in the `brand` object in `src/lib/site/site.ts`. Keep both in step. |
| Add a page | a new file in `src/content/pages/`, registered in `src/content/pages/index.ts` | The route, the sitemap and the metadata all follow from that one registry entry. |
| Add a new *kind* of section | a schema file, a component, and one line in `src/components/contentBlocks/Blocks.tsx` | A fixed sequence of files. [3. Adding things](?path=/docs/for-developers-3-adding-things--docs) walks through it. |
| Who may do what in the dashboard | a new SQL file in `supabase/migrations/` | **Never** in React. The React checks only decide what to draw — see [1. Architecture](?path=/docs/for-developers-1-architecture--docs). |

> **The files in `src/content/` are a fallback, not the live content.** As soon as
> `SUPABASE_SERVICE_ROLE_KEY` is set in the environment — and it is, on every real build — the
> accessors in `src/lib/site/content/` read pages and site chrome from Supabase instead, and these
> files are ignored. Editing them then changes nothing on the live site; that goes through `/builder`
> or the database. `src/content/README.md` spells out the traps in full, including what
> `npm run seed` overwrites.
