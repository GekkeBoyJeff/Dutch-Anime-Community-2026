# 4. Content & data

The public pages of this site are not written as markup. They are written as data: a TypeScript
object per page, listing which sections appear and what text goes in them. This page covers what that
object looks like, where its shape is defined, and where the site reads it from when it builds.

## A page is one object

This is `src/content/pages/word-lid.ts`, with the middle cut out.

```typescript
import type { Page } from '@/lib/site/content';

export const wordLidPage: Page = {
	meta: {
		title: 'Word lid',
		description:
			'In één minuut binnen, gratis, zonder apart account. Alle leeftijden, en je mag eerst een tijdje alleen meelezen.',
	},
	blocks: [
		{
			type: 'hero',
			id: 'intro',
			colorset: 'dark',
			variant: 'panel',
			tagline: 'Twijfel je nog?',
			title: 'In één minuut binnen, gratis',
			value: 'Geen apart account, geen verplichtingen. Je klikt, je bent binnen.',
			media: { type: 'image', src: '/media/dac-meetup.png', alt: 'DAC-leden samen op een meetup' },
			actions: [{ value: 'Word lid', variant: 'primary', url: 'https://discord.gg/dutchanimecommunity', target: '_blank' }],
			stats: [
				{ count: 'Gratis', label: 'altijd' },
				{ count: 'Alle', label: 'leeftijden' },
			],
		},
		{
			type: 'steps',
			id: 'zo-werkt-het',
			colorset: 'light',
			variant: 'process',
			heading: { tagline: 'De eerste vijf minuten', title: 'Zo gaat het' },
			items: [
				{ id: 'stap-1', title: 'Join de Discord', value: 'Eén klik op Word lid.' },
				{ id: 'stap-2', title: 'Kies je rollen', value: 'Vink aan wat je leuk vindt.' },
			],
		},
		// … six more blocks
	],
};
```

Every part of that has a job.

| Part | What it is |
| --- | --- |
| `meta.title`, `meta.description` | The `<title>` and meta description of the page. Both are required and may not be empty. |
| `meta.image`, `meta.structuredData` | Optional. A bespoke share image, and extra schema.org nodes. See [6. SEO & sharing](?path=/docs/for-developers-6-seo-sharing--docs). |
| `blocks` | The sections of the page, top to bottom. Reorder the array, and the page reorders. |
| `type` | Which section this is. It decides which React component renders it. |
| `id` | Optional on a block. It is the React key `Blocks.tsx` renders it with, and the handle `/builder` keeps a block identified by. |
| everything else | The props of that one block. Different per `type`. |

The page is registered in `src/content/pages/index.ts`, which maps a route to a page object:

```typescript
export const pages: Record<string, Page> = {
	'/': homePage,
	'/community': communityPage,
	'/evenementen': evenementenPage,
	'/supporters': supportersPage,
	'/word-lid': wordLidPage,
};
```

There is no route file per page. `src/app/(website)/[...slug]/page.tsx` is a catch-all: it asks for
every known path, then renders whichever page object belongs to the path being visited.

## The shape lives in `src/lib/site/content/schema/`

Every block has a schema — a description of its fields, written with [Zod](https://zod.dev). Zod is a
library for describing the shape of data in code, so the shape can be checked while the program runs.

The folder has three layers.

| Path | Holds |
| --- | --- |
| `schema/primitives.ts` | Pieces shared by many blocks: `Colorset`, `Id`, `Media`, `Action`, `Heading`, `OgImage`. |
| `schema/blocks/<name>.ts` | One file per block type. |
| `schema/blocks/index.ts` | The union of all block types. |
| `schema/document.ts` | `PageMeta` and `Page` — the object at the top of a content file. |

`schema/basics/`, `schema/components/`, `schema/forms/` and `schema/structures/` sit alongside
them; `schema/index.ts` re-exports the lot.

### A shared primitive

`Colorset` is defined once and reused by nearly every block:

```typescript
export const Colorset = z.enum(['light', 'dark']).meta({ title: 'Colorset' });
export type Colorset = z.infer<typeof Colorset>;
```

That pattern — a `const` holding the schema, and a `type` of the same name derived from it with
`z.infer` — is used everywhere in this folder. Importing the name gives you whichever of the two the
position needs.

### A block file

Every block file exports three things. `src/lib/site/content/schema/blocks/reviews.ts` in full:

```typescript
export const ReviewItem = z
	.object({
		id: Id,
		author: z.string().min(1).describe('Name of the reviewer, shown below the review text'),
		rating: z.number().int().min(1).max(5).describe('Star rating given by the reviewer, rendered as filled stars out of 5'),
		value: z.string().min(1).describe('Review text/testimonial content'),
	})
	.meta({ title: 'ReviewItem' });

export const ReviewsProps = z
	.object({
		colorset: Colorset.optional().describe('Light/dark theme applied to the surrounding section'),
		title: z.string().optional().describe('Main heading of the reviews section'),
		intro: z.string().optional().describe('Supporting introductory text rendered below the title'),
		subject: z.string().optional().describe('Name of the reviewed entity for the JSON-LD rich snippet; defaults to the site name when omitted'),
		items: z.array(ReviewItem).min(1).describe('List of reviews rendered as cards in the grid'),
	})
	.meta({ title: 'Reviews' });

export const ReviewsBlock = ReviewsProps.extend({ type: z.literal('reviews'), id: Id.optional() });
```

- `ReviewItem` — one row of a list. Its `id` is **required**, unlike the block's own `id`.
- `ReviewsProps` — the props of the React component, without `type` and `id`.
- `ReviewsBlock` — the same props plus `type: 'reviews'` and an optional `id`. This is the form that
  appears in a content file.

> **Why is a list item's `id` required when the block's is not?** A block has an index in the array to
> fall back on, so `Blocks.tsx` keys it as `${type}-${index}` when `id` is absent. A list item is
> reordered and edited in the visual builder, where an index is not a stable identity.

### The union

`schema/blocks/index.ts` collects every block into one schema:

```typescript
export const Block = z.discriminatedUnion('type', [
	HeroBlock,
	CardGridBlock,
	FeatureCardsBlock,
	// … 28 in total
]);
export type Block = z.infer<typeof Block>;
```

A discriminated union is a list of alternatives where one field decides which alternative applies —
here, `type`. Read `type: 'reviews'` and every other field must match `ReviewsBlock`; nothing else in
the list is considered.

That is what makes the error messages precise. An unknown `type` is reported once, against `type`,
with the valid names listed — not as 28 separate "this does not match" complaints.

`schema/document.ts` puts the last lid on it:

```typescript
export const Page = z.object({
	meta: PageMeta,
	blocks: z.array(Block),
});
export type Page = z.infer<typeof Page>;
```

## One schema, four consumers

The point of writing the shape down once is that four unrelated parts of the codebase read it.

| Consumer | Reads | Where |
| --- | --- | --- |
| TypeScript types | `z.infer` | every schema file, and `Blocks.tsx` |
| The runtime check | `Page` | `src/lib/site/content/pages.ts` |
| The Storybook props panel | the story's `jsonSchema` parameter | `.storybook/addons/json-schema/` |
| The `/builder` visual editor ([9. The visual editor](?path=/docs/for-developers-9-the-visual-editor--docs)) | `Block.options` | `src/lib/admin/puck/config.tsx` |

**Types.** No block type is hand-written. `type ReviewsProps = z.infer<typeof ReviewsProps>` derives
it, and `Reviews.tsx` imports that type for its props. The render registry in
`src/components/contentBlocks/Blocks.tsx` is typed by mapping over the union:

```typescript
type BlockRenderers = {
	[B in Block as B['type']]: BlockRenderer<Omit<B, 'type' | 'id'>>;
};

export const REGISTRY: BlockRenderers = {
	hero: Hero,
	cardGrid: CardGrid,
	// … one entry per member of the union
};
```

Add a block to the union and forget the registry entry, and `npm run typecheck` fails on the missing
key. The two cannot drift.

**The runtime check.** Content is parsed against `Page` before anything renders it. That is
[5. Validation](?path=/docs/for-developers-5-validation--docs).

**Storybook.** A block story names its schema in a parameter:

```tsx
parameters: {
	jsonSchema: { schema: ReviewsProps },
},
```

Two things follow from that line. The addon converts the schema to JSON Schema and copies each
`.describe()` text into the matching control's description in the **Controls** panel, marking
required props required — docgen alone cannot do this, because a prop type that is `z.infer<…>`
reaches it as a blank alias. It also validates the story's current args on every render and reports
the result in the **JSON Schema** panel next to Controls. Fiddle a control into an invalid state and
the panel says which field and why. See [ContentBlocks → Reviews](?path=/docs/contentblocks-reviews--docs).

**The builder.** `/builder` declares no components of its own. It walks the union:

```tsx
Block.options.map((blockSchema) => {
	const type = blockSchema.shape.type.value as keyof typeof REGISTRY;
	const Renderer = REGISTRY[type];
	// `type` is the discriminator and `id` is Puck's own instance key — neither is a field.
	const shape = Object.entries(blockSchema.shape).filter(([key]) => key !== 'type' && key !== 'id');
	// …
});
```

Each remaining property becomes an editor field, chosen by `fieldFor` in
`src/lib/admin/puck/fields.tsx`: a string becomes a text input, a number a number input (with the
`min`/`max` from the schema), an enum a dropdown, an array of objects a repeatable list. A property
whose schema `fieldFor` has no widget for returns `undefined` and simply does not appear in the
editor.

`.meta({ editor: '…' })` on a string overrides the default text input:

| `editor` | Widget |
| --- | --- |
| `textarea` | Multi-line text |
| `richtext` | Rich-text editor |
| `icon` | Dropdown of the project's icon names |
| `file` | Media picker |

## Where content comes from

There are two sources, and the site reads exactly one of them per build.

- **The registry** — the typed files in `src/content/`, shown above.
- **Supabase** — a `pages` table, edited through `/builder` by staff.

`src/lib/site/content/pages.ts` decides:

```typescript
export const dbEnabled = () =>
	env.CONTENT_SOURCE ? env.CONTENT_SOURCE === 'supabase' : Boolean(env.SUPABASE_SERVICE_ROLE_KEY);
```

| `CONTENT_SOURCE` | `SUPABASE_SERVICE_ROLE_KEY` | Source |
| --- | --- | --- |
| `supabase` | any | Supabase |
| `registry` | any | `src/content/` |
| unset | set | Supabase |
| unset | unset | `src/content/` |

Anyone who can deploy has that key in their `.env.local`, so **the default on a normal machine is
Supabase.** Editing a file in `src/content/pages/` then changes nothing you can see. To work on those
files, force the source:

```bash
npm run dev:local                                   # CONTENT_SOURCE=registry next dev
SUPABASE_SERVICE_ROLE_KEY= npm run build:plain      # for a build
```

When Supabase is the source, one more variable picks the column:

```typescript
// The live build reads `published_data` (CONTENT_CHANNEL=published); staging and local read `data`.
export const contentColumn = () => (env.CONTENT_CHANNEL === 'published' ? 'published_data' : 'data');
```

So a row carries two versions of the same page: `data` is the working copy an editor is changing, and
`published_data` is what the live build takes. A page whose chosen column is empty is treated as a
genuine 404 rather than an error.

The site-wide chrome — navigation, footer — works the same way, through
`src/lib/site/content/structures.ts` and `src/content/structures.ts`.

> `npm run seed` writes the files in `src/content/` **over** the database's `data` column, discarding
> anything edited through the builder. It is a one-off migration script, not a sync.

## Adding a field to an existing block

Say a review should be able to carry the date it was written.

1. **Add it to the schema.** In `src/lib/site/content/schema/blocks/reviews.ts`, inside `ReviewItem`:

   ```typescript
   date: z.string().optional().describe('Date the review was written'),
   ```

   Optional, because every review already in the content files and in the database lacks it. A
   required field would invalidate all of them at once.
   → verify: `npm run typecheck` passes.
2. **Render it.** `src/components/contentBlocks/Reviews.tsx` already types its props as
   `ReviewsSchemaProps`, so `review.date` is available with no further wiring. Use it in the JSX.
   → verify: `npm run typecheck` passes.
3. **Style it,** if it needs styling, in `src/styles/components/contentBlocks/Reviews.scss`.
   → verify: it looks right in Storybook.
4. **Show it in the story.** Add `date` to one item in the `args` of
   `src/stories/contentBlocks/Reviews.stories.tsx`.
   → verify: the control appears in **Controls**, carrying your `.describe()` text.
5. **Use it in content,** in `src/content/pages/*.ts` — or leave it out; it is optional.
   → verify: `SUPABASE_SERVICE_ROLE_KEY= npm run build:plain` succeeds and renders the new field.

Nothing needs to be done for `/builder`. The field appears there on its own, because the editor is
built from the same schema you just edited.

To add a whole new block rather than a field, see
[3. Adding things](?path=/docs/for-developers-3-adding-things--docs).
